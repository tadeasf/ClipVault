# ClipVault session handshake, v1 (`clipvault-hs-v1`)

Status: step 6 part A, spec for review. No code yet.

This handshake authenticates two paired devices, gives every connection fresh keys, and seals the
sync envelopes of [protocol.md](protocol.md). Pairing (how two devices first learn each other's
identity keys) is in [pairing.md](pairing.md). Both use this handshake, with a pairing mode.

## 1. Threat model

**The attacker** is on the same LAN. They can read, inject, drop, reorder and replay any packet,
and run a full man-in-the-middle. They can also open their own connections to any device.

**We assume:**
- The primitives hold: X25519, Ed25519, HKDF-SHA256, HMAC-SHA256 and XChaCha20-Poly1305.
- Devices are trusted while they are paired. A paired device may read everything that is synced
  to it.
- A **stolen device's long-term identity key is compromised.**

**Goals:**
- **Mutual authentication:** each side knows the other is a paired device, and which one.
- **Confidentiality and integrity of every sync frame:** no replay, no reflection, no reordering.
- **Forward secrecy:** recorded past sessions stay secret even after a device and its identity key
  are stolen. Session keys come only from ephemeral X25519 keys, which are erased after use.
- **Revocation:** once the user unpairs a device on their other devices, its handshakes fail there
  (section 6, pairing.md section 4). There is no central revocation (pairing.md section 4).
- **No identity in clear:** identity keys never cross the network unencrypted. They are known only
  from pairing.

**Not goals:**
- Hiding that ClipVault traffic exists, or its timing and size.
- Defending against denial of service from the LAN. We limit cost (section 3.6) and nothing more.
- **Lockouts keyed by source IP can be abused, and we accept that.** An attacker on the LAN can
  spoof a real peer's IP and fail handshakes on purpose, so the peer is locked out (3.6). That's
  why a lockout only blocks *new* handshakes from the address and never touches an established
  session.
- Protecting the data at rest on a stolen device. That is the job of the database encryption and
  the OS.

## 2. Keys and primitives

| Key | Type | Lifetime | Where |
|---|---|---|---|
| Identity `id_X` | Ed25519, 32-byte seed | per device, generated by ClipVault when sync is first enabled | `Identity` table in `SyncDatabase`, which is encrypted with the existing `DbKeyProvider` key (decided 2026-10-28) |
| Ephemeral `eph_X` | X25519, 32-byte scalar | one handshake | memory only; zeroed after key derivation |
| Peer identities | Ed25519 public, 32 bytes | until unpaired | `PeerIdentity` table in `SyncDatabase` (pairing.md section 3) |

**Primitive sources.** I checked the class and method signatures with `javap` against
`tink-1.24.0.jar` (the latest on Maven Central) and `bcprov-jdk18on-1.86.jar`. Behaviour has not
been exercised yet. That is what the test vectors in section 7 are for.

**Finding, stated now:**
- Tink's raw X25519, Ed25519 and HKDF are usable, but they live in `subtle`, outside Tink's keyset
  API.
- The counter-nonce AEAD this design needs is only in Tink's `internal` package, which a library
  can change without notice. I could not find Tink's written API-stability policy to say more.
- BouncyCastle 1.86 has every primitive above in its lightweight API. It is already a dependency
  (Argon2id on desktop), and pairing needs it anyway for EC J-PAKE.
- **Decided (2026-10-28): BouncyCastle 1.86 for every primitive, and no Tink.** That means one
  crypto library and no internal APIs. The Tink column above is kept only as the record of why.
- **Android:** an app-bundled `org.bouncycastle` must coexist with the platform's
  `com.android.org.bouncycastle`. That was checked on the device in step 6 part B (design 7). R8
  keep rules are in `sync-core/consumer-rules.pro`.

## 3. The handshake (SIGMA-I style)

### 3.1 Notation

| Symbol | Meaning |
|---|---|
| `\|\|` | byte concatenation |
| `u8(x)`, `u32be(x)`, `u64be(x)` | unsigned integers, big-endian |
| `lp(x)` | `u32be(len(x)) \|\| x`; every transcript element is length-prefixed |
| `H(x)` | SHA-256, 32 bytes |
| `HKDF(ikm, salt, info, L)` | HKDF-SHA256 (RFC 5869), extract then expand, L bytes |
| `HMAC(k, m)` | HMAC-SHA256, 32 bytes |
| `SIGN(sk, m)`, `VERIFY(pk, m, sig)` | Ed25519 (RFC 8032, pure, no context), 64-byte signatures |
| `DH(sk, pk)` | X25519 (RFC 7748), 32 bytes. **An all-zero result aborts** (low-order point). |

All labels are ASCII strings without a terminator, prefixed by `lp` where they are used.

**Roles:** **A** is the initiator (opens the TCP connection) and **B** is the responder. The role
is per connection, not per device type.

**Modes** (`u8`):
- `0x01 SESSION`: both sides already paired; KK.
- `0x02 PAIR_QR`: binding is the QR token.
- `0x03 PAIR_CODE`: binding is the J-PAKE key.

**`binding`** is empty in `SESSION`, the 16-byte token in `PAIR_QR`, and the 32-byte `k_pake` in
`PAIR_CODE` (pairing.md). It is never sent. It only enters the transcript.

### 3.2 Messages

Every message on the stream is `u32be(len) || body`. A handshake body over 256 bytes aborts.

**Init (A→B), 71 bytes:**

```
u8 0x01 || "CVHS" || u8 version=1 || u8 mode || eph_A.pub (32) || nonce_A (32)
```

**Resp (B→A), 161 bytes in SESSION, 97 in pairing modes (no `sig_B`):**

```
u8 0x02 || eph_B.pub (32) || nonce_B (32) || sig_B (64) || mac_B (32)
```

**Fin (A→B), 97 bytes in SESSION, 33 in pairing modes (no `sig_A`):**

```
u8 0x03 || sig_A (64) || mac_A (32)
```

`nonce_A` and `nonce_B` are 32 bytes from a CSPRNG.

### 3.3 Transcript and what is signed and MACed

```
T1 = lp("clipvault-hs-v1") || lp(u8 mode) || lp(eph_A.pub) || lp(nonce_A)
     || lp(eph_B.pub) || lp(nonce_B) || lp(binding)
h1 = H(T1)

sig_B = SIGN(id_B, lp("clipvault-hs-v1 sig B") || lp(h1))                       SESSION only
mac_B = HMAC(k_mac_B, lp("clipvault-hs-v1 mac B") || lp(h1) || lp(idpub_B))    idpub_B = "" in pairing modes

T2 = T1 || lp(sig_B) || lp(mac_B) || lp(idpub_B)       sig_B, idpub_B = "" in pairing modes
h2 = H(T2)

sig_A = SIGN(id_A, lp("clipvault-hs-v1 sig A") || lp(h2))                       SESSION only
mac_A = HMAC(k_mac_A, lp("clipvault-hs-v1 mac A") || lp(h2) || lp(idpub_A))    idpub_A = "" in pairing modes

T3 = T2 || lp(sig_A) || lp(mac_A) || lp(idpub_A)
h3 = H(T3)        the session id; pairing signs it (pairing.md section 3)
```

As in SIGMA-I:
- each side **signs** the ephemeral exchange with its role label;
- each side **MACs its own identity** under a key derived from the DH, which ties that identity to
  this key exchange;
- A's signature covers `h2`, which contains B's identity, so A also commits to who it is talking to.

### 3.4 Finding the peer without sending identities

Neither message names an identity. Discovery advertises a rotating random name (design 5.4), so A
may not know which paired device it reached either.

**A on Resp:**
1. Compute the keys (section 4).
2. For each paired peer P, check `VERIFY(P.pub, sig message, sig_B)`.
3. For the one that verifies, require `mac_B` with `idpub_B = P.pub` (constant-time compare).
4. If no peer verifies, abort.

**B on Fin:** the same, with `sig_A` and `mac_A`.

**Limits:**
- At most 32 paired peers, so this is at most 32 Ed25519 verifications.
- A device's own key is never in its paired set.
- A revoked peer is not in the paired set. Pending revokes are the exception (pairing.md
  section 4).

### 3.5 Order of checks

1. B on Init:
   - check type, magic, version and mode;
   - a pairing mode is accepted only while a pairing window is open on B;
   - generate `eph_B`, compute `DH`, abort on an all-zero result, derive keys, send Resp.
2. A on Resp: as 3.4. In pairing modes there is no signature, and `mac_B` with an empty identity is
   checked instead; it can only be right if B knew `binding`.
3. B on Fin: as 3.4, or the empty-identity `mac_A` in pairing modes.
   - **In pairing modes, the identity exchange (pairing.md section 3) is mandatory before any sync
     frame.** Each side accepts only `identity`, `pair_confirm` and `bye` until pairing has
     completed on its side.
   - A sync frame that arrives first aborts the connection.
4. Both erase the `eph` secrets and the DH output once the keys exist. After Fin, A may send
   transport frames at once. B sends none until Fin has verified.

### 3.6 Failure handling

**Any failure aborts.** The connection closes at once, with no error message, so there is no
oracle. Failures include:
- a malformed, oversized or unexpected message;
- an unknown version or mode;
- an all-zero DH output;
- no paired key verifies;
- a MAC mismatch;
- a timeout: 10 s per message, 30 s for the whole handshake.

The ephemeral secrets are erased. The log gets the failure class, the peer address and the first
8 hex characters of `h1`. Keys are never logged.

- **Backoff (A):** per peer address, 1 s doubling up to 5 min. It resets after a successful
  handshake.
- **Lockout counter (B):** failed handshakes per source IP in a sliding 10-minute window. At 10,
  B refuses *new* handshakes from that IP for 10 minutes: it closes them as soon as they are
  accepted.
  - An established session from that IP is never closed by a lockout. Source IPs can be spoofed
    on a LAN (section 1, not goals).
  - Pairing modes have their own, stricter limits (pairing.md).

## 4. Key derivation

```
ss      = DH(eph_A, eph_B.pub) = DH(eph_B, eph_A.pub)             32 bytes, abort if all zero
k_AB    = HKDF(ss, h1, "clipvault-hs-v1 key A->B", 32)           frames A to B
k_BA    = HKDF(ss, h1, "clipvault-hs-v1 key B->A", 32)           frames B to A
k_mac_A = HKDF(ss, h1, "clipvault-hs-v1 mac A", 32)
k_mac_B = HKDF(ss, h1, "clipvault-hs-v1 mac B", 32)
```

- These are four independent HKDF calls with the same extract step (salt `h1`) and different
  `info`.
- Because `binding` is part of `T1`, and so of the salt, nobody without the token or PAKE key can
  derive any of these keys. That is what authenticates pairing.
- The MAC keys are used only inside the handshake.

## 5. Transport

**Frame on the stream:** `u32be(len) || header (12) || ciphertext`

```
header = "CV" || u8 frame_version=1 || u8 flags=0 || u64be counter
nonce  = u64be(counter) || 16 zero bytes                           24 bytes
ct     = XChaCha20-Poly1305(key = k_AB or k_BA, nonce, aad = header, plaintext)
```

- **Plaintext:** one CBOR `Envelope` (protocol.md section 3).
- **`Envelope.seq` must equal `counter`.** That is the per-direction counter protocol.md reserved
  for this.
- **Counter:** starts at 1 in each direction and must be exactly the previous value + 1.
  - In particular, anything at or below the last seen value is rejected.
  - TCP keeps order, so a gap means frames were lost or injected, and the connection is broken
    anyway.
- **Size limit:** a `len` over 2 MiB + 28 aborts before reading. That covers the 1 MiB payload cap
  plus overhead.
- **Any authentication failure, counter mismatch or seq mismatch closes the connection.** No error
  frame is sent. `Bye` is a normal encrypted frame and is sent only on orderly closes.
- **Every connect runs a new handshake.** There is no session resumption, and there is no
  in-session rekey in v1.
- **Session limit:** at 2^32 frames in either direction or 24 h after the handshake, whichever is
  first, the session closes and the devices reconnect with a new handshake.
- **Nonce reuse is impossible:** a key lives for one session and one direction, and its counter
  never repeats.

## 6. Replay and reflection

| Attack | Why it fails |
|---|---|
| Replayed Init | B answers with a fresh `eph_B` and `nonce_B`. Without `eph_A`'s secret the attacker can't derive `k_mac_A`, and an old `sig_A` covers an old `h2`. Fin fails, and the attempt counts towards the lockout. |
| Replayed Resp (to a new Init from A) | `sig_B` and `mac_B` cover `h1`, which contains A's fresh `eph_A` and `nonce_A`. A rejects it. |
| Replayed Fin | `sig_A` and `mac_A` cover the old `h2`. B rejects it. |
| Reflection (A's own messages played back to A as responder) | Signatures carry the role labels `sig A` / `sig B`, so one can't stand in for the other. A device's own identity is never in its paired set, so it can't authenticate itself. |
| A→B frame replayed as B→A | B→A frames are opened with `k_BA`. A frame sealed under `k_AB` fails authentication. |
| Frame replayed within a direction or across sessions | Within a session, the counter must be last + 1. A new session has new keys. |
| Stolen identity key | The thief can impersonate that device until it is unpaired. Past sessions stay secret (ephemeral-only keys). It does not let them impersonate *other* devices to the victim: that would need their signing keys. |

## 7. Test vectors

- **File:** `sync-core/src/commonTest/resources/handshake-vectors.json`.
- **Generator:** an independent Python reference, `tools/handshake_vectors.py`, written from this
  document and not from the Kotlin code. It uses `cryptography` for X25519, Ed25519, HKDF, HMAC
  and SHA-256, and **PyNaCl 1.6.2** for
  `nacl.bindings.crypto_aead_xchacha20poly1305_ietf_encrypt(message, aad, nonce, key)` (signature
  checked in its source). `cryptography` itself has no XChaCha20-Poly1305: its AEAD page lists
  `ChaCha20Poly1305` and the AES modes only.
- **Inputs:** all fixed, so every output is deterministic (Ed25519 is deterministic).

  | Input | Value |
  |---|---|
  | `eph_A` secret | bytes `0x00..0x1f` |
  | `eph_B` secret | bytes `0x20..0x3f` |
  | `id_A` seed | bytes `0x40..0x5f` |
  | `id_B` seed | bytes `0x60..0x7f` |
  | `nonce_A` | 32 × `0xa1` |
  | `nonce_B` | 32 × `0xb2` |
  | QR token | 16 × `0x7e` |
  | `k_pake` | 32 × `0x5c` |

- **Content:**
  - For each mode (`session`, `pair_qr`, `pair_code`): the Init, Resp and Fin bytes, `T1`, `h1`,
    `ss`, the four keys, `sig_B`, `mac_B`, `h2`, `sig_A`, `mac_A` and `h3`.
  - Frames: one A→B frame with counter 1 and one B→A frame with counter 2^32−1, both with
    plaintext `"clipvault test frame"`, with header, nonce, AAD and ciphertext.
  - Negative cases that must fail: a frame with one tag bit flipped, the A→B frame opened with
    `k_BA`, and a Fin from the `session` vectors replayed against a fresh Resp.
  - All bytes are lowercase hex.
- **Use:**
  - A Kotlin commonTest (`HandshakeVectorsTest`) must reproduce every value byte for byte.
  - CI also runs `python3 tools/handshake_vectors.py --check`, which regenerates the file and fails
    if it differs from the committed one. Python and Kotlin then can't drift apart.

## 8. Compared with Noise KK

Noise KK (`Noise_KK_25519_ChaChaPoly_SHA256`, https://noiseprotocol.org/noise.html) solves the same
problem: both static keys known in advance, mutual authentication, forward secrecy, two messages.

| | Noise KK | This design |
|---|---|---|
| Authentication | DH between static and ephemeral X25519 keys | Ed25519 signatures over the transcript plus identity MACs (SIGMA-I, the pattern behind IKEv2 signature authentication) |
| Round trips | 2 messages | 3 messages |
| Key confirmation | implicit | explicit (`mac_A`, `mac_B`) |
| Peer identification | needs a pre-known peer | trial verification over the paired set (section 3.4) |
| Formal analysis | covers Noise's exact patterns | none of our own; we rely on SIGMA's analysis |

**Why the deviations are acceptable:**
- There is no maintained Noise implementation for the JVM (design 5.2).
- SIGMA-I is a well-studied construction.
- On a LAN the third message costs about a millisecond.
- Signature identities give the stable key that the pairing fingerprint words are made from.

**What we give up:** the extra assurance of the Noise framework's formal analysis covering exactly
the pattern we run. The composition is ours, so it gets the test vectors above and an explicit
request for external review before release.
